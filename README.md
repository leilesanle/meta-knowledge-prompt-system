# 元知识驱动的问题解决系统

## 它解决什么问题

AI 回答专业问题时容易泛泛而谈、不查方法、不区分"这题该不该用专业框架"。
这套系统让 AI 先定位"问题类型 → 可用方法"，再补名词，最后解决；
并且用入库闸和日志保证它真的在查、在用，而不是嘴上说查了。

## 入口是自然语言：你说大白话，行话在系统内部解决

这套系统的调用方是 AI，不是人。完整链路是：

**人话原句 → AI 先按「提示词优化」（M021）把大白话换成专业名词 → 关键词检索命中方法卡 → 按卡执行 → 回执注明条目 ID**

实测一例（2026-11-07）：

> 问：「我想用一张照片加一段录音，做条能发抖音的口播视频，动手前该先弄明白什么、最容易在哪儿翻车？」
> AI 拆词（口型同步／活底片／口播）→ 命中 M014·口型同步出片 → 按卡答出母版标准、音频规格、路线选型与该卡的翻车误区。

先把边界说清，免得误会：检索器本身只做关键词匹配，**整句丢给它命中是 0**——这不是缺陷，是分工：理解人话、拆关键词是前置层（AI＋提示词优化）的活，检索器只负责按名词精确调卡。同组 7 道实测题按这条链路走，命中 7/7；验收指标因此定为「优化后提示词的一次通过率」，不拿整句直检冒充能力。

配套文档：`PROMPT_OPTIMIZATION.md`（提示词优化全文）。

## 和普通 prompt 合集有什么区别

- 三层结构：问题类型索引 → 方法卡 → 名词表（名词挂在方法下讲作用，不孤立囤定义）
- 入库有闸：溯源三问 + 费曼闸 + 入库消融 + 查重两道，不过闸不收
- 触发有判据："去掉这个名词，解法会不会出错或降级"，该豁免时干净豁免
- 过程有日志：翻车记录、版本线、消融基线，可复现、可审计

## 怎么用（两种方式，任选）

**方式一：粘贴给 AI**
把 RULES.md 全文粘进自定义指令／项目规则，词典（dictionary/terms.json）放知识库。

**方式二：本地跑检索器**

```
python scripts/find_term.py "银行对账"
python scripts/find_term.py --index        # 问题类型索引
python scripts/find_term.py --card M009    # 调一张方法卡全文
python scripts/find_term.py --flows       # 流程卡（编排层）简表
python scripts/find_term.py --flow F001   # 调一张流程卡全文
```

## 词典里有什么

30 类问题索引 / 26 张方法卡 / 68 个名词 / 2 条长期原则（P001 先学名词后解问题、P002 收集与应用机制）/ 1 张流程卡（F001·数字人口播生产，编排层：把多张方法卡按真实生产顺序串成流水线）。
示例：M009 银行余额调节、M002 蒙特卡罗模拟、M014 口型同步出片、M021 提示词优化。
每张卡含：解决什么问题、触发条件、核心步骤、判断标准、常见误区、原初问题、前提假设、费曼自述。

命中已画未建的格，系统只报"此格已画未建"，不瞎编卡——实例见 examples/。

## 它不是万能的

- 检索是关键词匹配（aliases 兜底），不是语义检索，换个说法可能漏检
- 方法卡深度靠一手经典补，考纲只画边界
- 待建格只报"已画未建"，不瞎编卡
- 这套系统在真实任务里长出来，卡的质量参差：标注了来源与置信度，单源经验卡会明说"待验证"

## 文件导览

- `RULES.md` — 规则全文（v1.3 定版＋补丁；词典数据版本见 VERSION_LOG）
- `PROMPT_OPTIMIZATION.md` — 提示词优化：把大白话任务翻成可执行提示词的八步方法（M021 的展开版）
- `dictionary/terms.json` — 词典数据（三层结构全量）
- `scripts/find_term.py` — 检索器（零依赖，Python 3 标准库）
- `scripts/check_reply.py` — 回复格式硬校验：两行起头／查证行／实测值／自查结论，发送前过闸（零依赖）
- `scripts/seal_metadata.py` — 发布前元数据闸门：交付信息四字段不全，不许进发布队列（零依赖）
- `RUNLOG.md` — 过程记录＋翻车与修复（这套系统怎么长出来的）
- `VERSION_LOG.md` — 版本线 v1.0 → v1.4
- `examples/` — 五个真实回执案例：命中／待建／豁免／跨域／别名
- `CONTRIBUTING.md` — 别人怎么加卡（必须走同样的闸）
